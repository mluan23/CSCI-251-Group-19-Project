## Build & Run Instructions

1. Ensure .NET 9.0 SDK is installed
2. Clone the repository
3. From the project root, run:
   ```
   dotnet build
   dotnet run
   ```
4. On one terminal, type `/listen <port>` to start a server (e.g., `/listen 5001`)
5. On another terminal, type `/connect <ip> <port>` to connect as a client (e.g., `/connect 127.0.0.1 5001`)
6. When prompted, enter your name
7. Type messages to chat, or use `/help` to see available commands
8. Chat room commands: `/create #room`, `/join #room`, `/leave #room`, `/rooms`, `/msg #room message`

## Security Protocol Overview

### Encryption Protocol

#### Key Exchange Process
When two peers connect, the following key exchange protocol is performed:

1. Client connects to the server via TCP
2. Client generates a 2048-bit RSA key pair (`KeyExchange` constructor creates `RsaEncryption`)
3. Client sends its RSA public key to the server (Base64-encoded over TCP)
4. Server generates its own 2048-bit RSA key pair and sends its RSA public key back to the client
5. Client receives the server's public key and stores it
6. Client generates a random 256-bit AES session key using `AesEncryption.GenerateKey()`
7. Client encrypts the AES session key with the server's RSA public key (OAEP-SHA256 padding)
8. Client sends the encrypted AES session key to the server
9. Server decrypts the AES session key using its RSA private key
10. Both client and server now share the same AES-256 session key (stored in `Peer.AesKey`)
11. Client then sends their username as plaintext
12. All subsequent text messages are encrypted with AES and signed with RSA

#### Message Encryption
Messages are encrypted using AES-256-CBC before being sent over the network. The server decrypts incoming messages with the sender's AES key, then re-encrypts for each recipient with their respective AES key.

- **Algorithm:** AES-256-CBC (Cipher Block Chaining)
- **Key Size:** 256 bits (32 bytes)
- **IV Generation:** A random 16-byte IV is generated for each message using `Aes.GenerateIV()`. The IV is prepended to the ciphertext so the receiver can extract it for decryption.

Wire format for encrypted messages: `[IV (16 bytes)][Ciphertext (variable length)]`

#### Message Signing
Each message is signed by the sender's RSA private key and verified by the receiver to ensure authenticity and integrity.

- **Algorithm:** RSA with SHA-256
- **Key Size:** 2048 bits
- **Padding:** PKCS#1 v1.5 (`RSASignaturePadding.Pkcs1`)

The sender signs the message content bytes using `KeyExchange.Sign()`, which delegates to `RsaEncryption.Sign()` and `MessageSigner.SignData()`. The sender's RSA public key is attached to each message in the `PublicKey` field. The receiver verifies the signature using `MessageSigner.VerifyData()` with the sender's public key. Messages with invalid signatures are rejected.

## Key Management

### Key Generation
- **RSA Key Pair (Client):** Generated when `KeyExchange` is created during `ConnectAsync()`. Uses `RSA.Create(2048)`.
- **RSA Key Pair (Server):** Generated when `TcpServer` is instantiated. The server has its own `RsaEncryption` instance for the key exchange handshake.
- **AES Session Key:** Generated by the client (initiator) during key exchange using `Aes.Create()` with `KeySize = 256`. A unique AES key is generated per client-server pair.

### Key Storage
All keys are stored in memory at runtime:
- Client RSA key pair: held inside `KeyExchange._rsa` (an `RsaEncryption` instance)
- Server RSA key pair: held inside `TcpServer._rsa` (an `RsaEncryption` instance)
- AES session keys: stored in `Peer.AesKey` for each connected peer (on both client and server side)
- Peer RSA public keys: stored in `Peer.PublicKey` for signature verification
- Message signatures and public keys are transmitted per-message in the `Signature` and `PublicKey` fields
- No keys are written to disk

### Key Lifetime
| Key Type | Generated When | Expires When |
|----------|----------------|--------------|
| RSA Key Pair (Client) | When `/connect` is called (KeyExchange constructor) | When the application exits |
| RSA Key Pair (Server) | When TcpServer is instantiated | When the application exits |
| AES Session Key | During key exchange after public keys are exchanged | When the peer disconnects (session ends) |

## Wire Protocol

### Message Format
```
Messages are sent as JSON-serialized lines over TCP using StreamWriter/StreamReader.
Each message is a single line terminated by a newline character.

Key exchange uses raw Base64 strings (one per line):
  Line 1: Client RSA public key (Base64)
  Line 2: Server RSA public key (Base64)
  Line 3: Encrypted AES session key (Base64)
  Line 4: Client username (plaintext)

Subsequent messages use JSON:
{"Id":"...","Sender":"Alice","Content":"...","Timestamp":"...","Signature":"<base64>",
 "EncryptedContent":"<base64>","PublicKey":"<base64>","Type":0,"Room":null,"TargetPeerId":null}
```

### Message Types
| Type | Name | Description |
|------|------|-------------|
| 0 | Text | Standard encrypted chat message (AES-encrypted content, RSA-signed) |
| 1 | KeyExchange | Key exchange messages (handled during connection setup) |
| 2 | Heartbeat | Reserved for Sprint 3 |
| 3 | PeerDiscovery | Reserved for Sprint 3 |
| 4 | Command | Room commands sent as messages (`/create`, `/join`, `/leave`) |
| 5 | RoomMessage | Message targeted to a specific chat room |

## Threat Model

### Assets Protected
- Message content (plaintext of chat messages)
- AES session keys (protected during exchange via RSA encryption)
- Message integrity and authenticity (RSA signatures detect tampering and verify sender)

### Threats Addressed
| Threat | Mitigation |
|--------|------------|
| Eavesdropping | AES-256-CBC encryption of all message content; server decrypts and re-encrypts per recipient |
| Man-in-the-middle | RSA public key exchange at connection time; AES session key encrypted with recipient's RSA public key |
| Message tampering | RSA digital signatures (SHA-256 + PKCS#1 v1.5) on all messages; receiver verifies with sender's public key; tampered messages are rejected |
| Replay attacks | Each message has a unique Guid (`Message.Id`) and timestamp; fresh AES session keys per connection |

### Known Limitations
- No certificate authority or trust-on-first-use (TOFU) mechanism — public keys are not independently verified, so a sophisticated MITM during the initial key exchange could substitute their own keys
- Keys are stored in memory without additional protection (could be read from a memory dump)
- No perfect forward secrecy — if the RSA private key is compromised, past session keys can be decrypted
- No protection against denial-of-service attacks
- Session keys last for the entire connection lifetime (no key rotation)
